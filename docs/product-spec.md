# 사이별 — MVP 제품 명세서 v0.1

2026-10-19 · 원본은 Claude Docs의 동명 문서이며, 이 파일은 그 내보내기본이다. 결정이 바뀌면 둘 다 고친다.

## 1. 서비스 정의와 Value Proposition

**사이별**은 내가 아는 사람과의 관계를, 관계마다 다르게 읽어주는 관계 이해 서비스다. 자기 분석 서비스도, 낯선 사람 매칭 서비스도 아니다. 태그라인은 "같은 나라도, 사이마다 다르게".

### 한 문단 버전

우리는 매일 가장 가까운 사람들과 부딪히면서도, 정작 그 사람이 왜 그렇게 말하고 왜 그렇게 반응하는지 설명할 언어를 갖고 있지 않습니다. 이 서비스는 나와 내 주변 사람 각자의 타고난 성향을 바탕으로, 두 사람 사이에 어떤 결이 맞고 어디서 마찰이 생기는지, 그리고 그 마찰을 어떻게 다루면 좋은지를 관계마다 다르게 풀어줍니다. 부모와 자녀, 오래된 친구, 연인 — 같은 나라도 상대에 따라 다른 사람이 되기 때문입니다. 한 사람씩 등록할 때마다 나를 둘러싼 관계의 지도가 그려지고, 함께 보낸 시간과 사건이 쌓일수록 그 해석은 점수가 아니라 서로를 더 잘 대하는 방법으로 깊어집니다. 우리는 사람을 분류하는 서비스가 아니라, 내가 아끼는 사람을 더 잘 이해하는 출발선이 되고자 합니다.

### 한 줄 버전 (앱스토어 부제, 랜딩 첫 화면)

가까운 사람일수록, 더 잘 이해할 방법이 필요합니다.

### 이름: 사이별

'사이'에 관계별·사람별의 '별'을 붙인 이름이다. 사람을 종류별로 나눈다는 뜻이 아니라, 누구와의 관계인지에 따라 다르게 읽어준다는 뜻이다. 엄마와 있을 때의 나, 친구와 있을 때의 나, 연인과 있을 때의 나, 동료와 있을 때의 나는 다르다. 이 서비스의 가장 중요한 차별점인 "관계마다 달라지는 해석"을 이름 자체에 담는다.

후보 중 서비스 정의와 가장 정확하게 맞닿아 있고, '사이'라는 직관성을 유지하면서 단순한 소통·연결 서비스에서 한 걸음 더 나아간다. 어느 관계에도 적용되며 기능명으로 이어진다. '사이별 기록', '사이별 대화 가이드', '나의 사이별 지도'.

### 세 층의 분리

| 층 | 내용 | 어디에 드러나는가 |
| --- | --- | --- |
| 비전 | 모든 관계를 이해하는 출발선. 장기적으로는 처음 만난 사람에게도 건네는 "나를 대하는 설명서" | 회사 미션, 투자 설명, 장기 로드맵 |
| 제품의 첫 문장 | 내가 아는 사람과의 관계를 각자 다르게 읽어준다 | 이름, 첫 화면, 앱스토어 설명, 공유 카드 |
| 해석 엔진 | 생년월일시 기반 성향 분석(첫 번째 엔진). 교체·추가 가능한 부품 | 설정 화면, 결과 카드 하단의 작은 출처 표기에만 |

"사주"라는 단어는 세 번째 층에만 속한다. 이름·첫 화면·앱스토어 설명 어디에도 주인공으로 쓰지 않는다. 사용자가 그 단어를 보는 순간 기존 운세 카테고리로 분류하기 때문이다.

## 2. 확정된 결정사항

2026년 10월 19일 기준으로 아래가 확정되었다. 이후 결정은 이 표에 행을 추가한다.

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 서비스 이름 | 사이별 | 관계마다 달라지는 해석을 이름에 담는다. "사주"가 들어가지 않는다 |
| 첫 관계 유형 | 가족·친구·연인·직장동료 | 가까운 사이는 입력 동기가 가장 강하다. 직장동료는 매일 부딪히는 사이이면서 비즈니스 확장의 가벼운 입구다. 동업·채용·거래처 같은 본격 비즈니스 관계는 레퍼런스가 쌓인 뒤 |
| 톤 | 겉은 가볍게(카드·공유·짧은 문장), 속은 진지하게(해설의 깊이) | 가벼움은 확산을, 깊이는 신뢰와 재방문을 만든다 |
| 입력 주체 | 양쪽 모두 본인이 직접 입력. 상대방 정보를 대신 입력할 수 없다 | 동의 기반 관계 활성화(특허 과제 5), 개인정보 보호 |
| 출생시간 | 생년월일 필수, 출생시간은 선택("모름" 허용). 없으면 신뢰도를 낮게 시작 | 본인 출생시간을 모르는 사람이 많고, 초대받은 쪽이 가장 약한 고리 |
| 사주의 위치 | 첫 번째 해석 엔진. 이름·첫 화면·스토어 설명에 쓰지 않는다 | 운세 앱으로 분류되는 순간 차별점이 사라진다 |
| 첫 버전의 목표 지표 | 수익이 아니라 "사용자가 관계를 계속 등록하는가" | 관계 그래프가 자산임을 증명하는 지표. 수익 구조는 비즈니스 확장 시 본격화 |

이전 기획 문서(특허 발명설명서 초안)의 핵심 개념은 그대로 유지한다. 원천정보 → 파생 프로파일 → 관계 유형별 정합도 → 관계 Edge → 개인 관계 그래프. 첫 버전은 이 중 앞 네 단계까지를 가장 단순한 형태로 구현한다.

## 3. 첫 버전 범위: 관계 유형 네 가지, 기능 다섯 개

첫 버전은 웹으로 만든다. 앱스토어, 연락처 자동 연동, 결제는 모두 뺀다. 링크 하나로 초대하고 링크 하나로 결과를 공유하는 것이 전부다.

### 관계 유형

| 유형 | 포함하는 관계 | 사용자가 고르는 화면의 표현 |
| --- | --- | --- |
| 가족 | 부모–자녀, 형제자매, 배우자, 조부모 | "가족" (세부 관계는 선택 입력) |
| 친구 | 오랜 친구, 최근 친해진 사람, 동호회·학교 친구 | "친구" |
| 연인 | 사귀는 사이, 썸, 배우자(연인으로서 보고 싶을 때) | "연인" |
| 직장동료 | 같은 팀 동료, 자주 협업하는 다른 팀 사람, 가까운 선후배·상사 | "직장동료" |

배우자는 가족과 연인 양쪽에 등록할 수 있다. 같은 두 사람이 관계 유형에 따라 다른 해설을 받는다는 것을 가장 직관적으로 보여주는 사례이므로, 결과 화면에서 "연인으로도 보기" 전환을 허용한다.

직장동료는 매일 함께 일하는 사이를 뜻하며, 평가·채용·동업 판단에 쓰는 유형이 아니다. 상사·부하도 등록할 수 있지만 해설은 협업 방식에 머물고 역량이나 서열을 말하지 않는다. 동업자·거래처·투자자 같은 본격 비즈니스 관계는 다음 버전이다(9절).

### MVP 기능 다섯 개

1. **내 프로필 카드** — 생년월일(필수)·출생시간(선택)·성별·이름을 입력하면 나의 성향을 담은 카드가 생성된다. 카드에는 원천정보(생년월일시)가 표시되지 않는다.
2. **초대 링크와 관계 활성화** — 내가 상대를 이름과 관계 유형으로 등록하면 고유 링크가 생성된다. 상대가 링크를 열어 본인 정보를 직접 입력하는 순간 관계가 "후보"에서 "활성"으로 바뀌고, 양쪽 모두 결과를 받는다.
3. **관계 유형별 해설** — 활성화된 관계에 대해, 선택한 유형(가족·친구·연인·직장동료)에 맞는 차원별 정합도와 해설 문장이 생성된다. 유형을 바꾸면 해설이 달라진다.
4. **내 관계 목록** — 나를 중심으로 등록한 사람들이 관계 유형별로 묶여 보인다. 관계 그래프의 가장 단순한 형태. 각 항목에서 상태(초대 대기 / 활성)와 핵심 한 줄을 볼 수 있다.
5. **결과 카드 공유** — 두 사람의 관계 카드를 이미지 또는 링크로 공유한다. 공유 카드에는 양쪽의 원천정보가 절대 포함되지 않으며, 해설의 일부만 노출하고 나머지는 서비스 안에서 보게 한다.

### 기능 간 의존

1 → 2 → 3 → 4 → 5 순서로 만든다. 1과 2가 끝나면 두 사람이 한 번 결과를 받아보는 흐름이 성립하므로, 그 시점에 첫 사용자 테스트를 시작한다. 4와 5는 테스트와 병행해 만든다.

## 4. 사용자 흐름

흐름의 핵심은 B의 입력이 두 사람 모두의 결과를 만든다는 점이다. A는 B가 입력하기 전까지 아무 결과도 받지 못한다.

```
A (초대하는 사람)
  내 정보 입력 → 프로필 카드 생성 → 상대 등록(이름·관계 유형) → 초대 링크 전송
                                                                      │ 링크
B (초대받은 사람)                                                     ▼
                                              링크 열기·안내 확인 → 본인 정보 입력 (= 관계 활성화)
                                                                      │ 후보 → 활성
                                                                      ▼
                                                            두 사람 모두 결과 카드 받기
```

A가 초대 링크를 보내면 관계는 "후보" 상태로 A의 목록에만 보인다. B가 링크를 열어 본인 정보를 직접 입력하는 순간 관계가 "활성"으로 바뀌고, 결과 카드가 양쪽 모두에게 열린다.

### 화면 순서 (A 기준)

1. 시작 화면 — 한 줄 가치 제안과 "내 카드 만들기" 버튼
2. 내 정보 입력 — 이름, 생년월일, 출생시간(모름 선택 가능), 성별, 양력/음력
3. 내 프로필 카드 — 성향 요약 카드. 아래에 "가까운 사람 등록하기"
4. 상대 등록 — 상대 이름(호칭), 관계 유형(가족·친구·연인·직장동료)
5. 초대 링크 — 복사 또는 메신저로 보내기. 보낸 뒤 "기다리는 중" 상태로 목록에 추가
6. 결과 카드 — B가 입력하면 알림. 관계 유형별 해설과 "다른 유형으로 보기"
7. 내 관계 목록 — 등록한 사람 전체, 상태와 핵심 한 줄

### 화면 순서 (B 기준)

1. 링크 열기 — "A님이 당신과의 관계를 알고 싶어 합니다" + A의 프로필 카드 일부(원천정보 없음)
2. 안내 — 무엇을 입력하고, 무엇이 공개되고, 무엇이 공개되지 않는지 세 줄
3. 본인 정보 입력 — A와 같은 항목
4. 결과 카드 — A가 보는 것과 같은 카드. 아래에 "나도 내 사람 등록하기"

B의 4번 화면이 이 서비스의 성장 경로다. B가 자기 사람을 등록하면 B는 A가 되고, 그래프가 한 칸 더 자란다. 이 전환율을 첫 버전의 두 번째 핵심 지표로 본다.

## 5. 입력 규칙과 신뢰도

생년월일은 필수, 출생시간은 선택이다. 출생시간이 없으면 해석은 생성되되 신뢰도가 낮게 시작하고, 나중에 추가하면 올라간다.

### 입력 항목

| 항목 | 필수 여부 | 비고 |
| --- | --- | --- |
| 이름(호칭) | 필수 | 상대에게 보이는 이름. 실명일 필요 없음 |
| 생년월일 | 필수 | 양력/음력 선택. 음력은 윤달 여부 포함 |
| 출생시간 | 선택 | "모름" 선택 가능. 입력 시 시간대(子~亥) 또는 시:분 |
| 성별 | 필수 | 해석 엔진이 대운 방향 계산에 사용 |
| 출생지역 | 첫 버전 제외 | 진태양시 보정은 다음 버전에서 검토 |

### 신뢰도(Confidence)의 첫 버전 규칙

첫 버전의 신뢰도는 학습된 값이 아니라 규칙으로 정한다. 출생시간 유무가 유일한 변수다.

| 상황 | 신뢰도 | 결과 카드의 표현 |
| --- | --- | --- |
| 양쪽 모두 출생시간 있음 | 높음 | 표기 없음 |
| 한쪽만 출생시간 있음 | 중간 | "OO님의 출생시간이 더해지면 더 정밀해져요" |
| 양쪽 모두 출생시간 없음 | 낮음 | "두 분의 출생시간이 더해지면 더 정밀해져요" |

출생시간이 없는 쪽은 시주(時柱) 없이 3주(年·月·日)로 파생 프로파일을 만든다. 시주 의존도가 높은 차원은 결과에서 숨기거나 "추정"으로 표기한다. 어떤 차원이 시주 의존인지는 7절의 해설 차원 표에 표시한다.

이 규칙은 특허 문서의 Predicted Compatibility와 Observed Relationship State 구분으로 가는 첫 단계다. 다음 버전에서 관계 이벤트가 들어오면 신뢰도의 두 번째 변수가 된다.

### 원천정보 비공개 원칙

- 생년월일, 출생시간, 원시 사주 데이터는 본인 외 누구에게도 표시하지 않는다. 상대방 화면, 결과 카드, 공유 이미지, 관계 목록 어디에도 없다.
- 상대방에게 보이는 것은 파생된 성향 요약, 관계 유형별 정합도, 해설 문장, 신뢰도 표기뿐이다.
- 서버는 원천정보와 파생 프로파일을 분리 저장하고, 관계 분석 로직은 파생 프로파일만 읽는다. 이 분리가 코드 구조에서 강제되어야 한다(6절).
- 사용자는 언제든 본인 원천정보를 삭제할 수 있다. 삭제 시 파생 프로파일과 모든 관계 Edge도 함께 비활성화된다.

## 6. 데이터 모델 뼈대

엔티티는 다섯 개다. User, SourceData, DerivedProfile, RelationshipEdge, 그리고 Edge 안에 관계 유형별로 담기는 CompatibilityVector와 Narrative. 설계의 핵심은 관계 분석 코드가 SourceData에 접근할 수 없도록 구조로 막는 것이다.

```
User A ──┐                                        ┌── User B
         ▼                                        ▼
  SourceData (비공개)                      SourceData (비공개)
  생년월일·출생시간·성별                    생년월일·출생시간·성별
         │ 파생                                   │ 파생
         ▼                                        ▼
  DerivedProfile ─────▶ RelationshipEdge A–B ◀───── DerivedProfile
                        state · types[] · vector · narrative · confidence

  Edge 상태:  candidate ──(B 입력)──▶ active ──(철회)──▶ revoked
```

SourceData는 본인만 읽고 쓸 수 있다. DerivedProfile은 SourceData에서 한 방향으로만 만들어지고, 관계 엔진은 두 DerivedProfile만 입력으로 받아 Edge를 채운다.

### 엔티티별 핵심 필드

| 엔티티 | 필드 | 누가 읽는가 |
| --- | --- | --- |
| User | id, displayName, createdAt, authProvider | 본인, 관계 상대(displayName만) |
| SourceData | userId, birthDate, calendarType(양력/음력), isLeapMonth, birthTime(nullable), gender | 본인만. 상대도 해설 엔진도 읽지 않는다 |
| DerivedProfile | userId, engine("saju"), engineVersion, hasBirthTime, pillars(시주는 nullable), elementDistribution, tenGods, traitDimensions, summaryText | 관계 엔진, 본인 프로필 카드 |
| RelationshipEdge | id, userAId, userBId, state, types[], inviteToken, createdAt, activatedAt, updatedAt | 양쪽 사용자(active일 때), A만(candidate일 때) |
| CompatibilityVector | edgeId, relationshipType, dimensions{name: score}, confidence, engineVersion, computedAt | 양쪽 사용자 |
| Narrative | edgeId, relationshipType, headline, sections[], shareableExcerpt, generatedAt | 양쪽 사용자. shareableExcerpt만 공유 카드에 |

### 설계 원칙 세 가지

1. **해석 엔진은 교체 가능한 모듈이다.** `DerivedProfile.engine` 필드가 그 자리다. 첫 버전은 "saju" 하나지만, 엔진 인터페이스는 `SourceData → DerivedProfile`과 `(DerivedProfile, DerivedProfile, type) → CompatibilityVector` 두 함수로 고정한다.
2. **Edge는 관계 유형을 여러 개 가질 수 있다.** 배우자 = 가족 + 연인. Vector와 Narrative는 유형별로 한 행씩 생긴다.
3. **삭제는 연쇄된다.** SourceData 삭제 → DerivedProfile 삭제 → 해당 사용자의 모든 Edge는 revoked. 상대방 화면에서는 "상대가 정보를 삭제했어요"로 바뀐다.

### 다음 버전을 위해 비워두는 자리

RelationshipEvent(edgeId, type, note, occurredAt)와 Edge의 `observedState`는 테이블만 설계해 두고 첫 버전에서는 만들지 않는다. 신뢰도가 규칙값에서 관측값으로 바뀔 때 여기에 붙는다.

## 7. 관계 유형별 해설 차원

관계 유형마다 보는 차원이 다르다. 같은 두 사람도 가족으로 보면 "기대와 역할"이, 연인으로 보면 "애정 표현과 거리"가 앞에 선다. 이 표가 CompatibilityVector의 `dimensions`를 정의하고, Narrative의 섹션 순서를 정한다.

이 표는 초안이다. 명리 해석의 어떤 요소(일간 관계, 오행 생극, 십신 배치, 지지 합충 등)가 각 차원에 대응하는지는 `docs/dimensions.md`에서 따로 정한다. 여기서는 사용자가 보는 차원과 그 의미만 고정한다.

### 공통 차원 (네 유형 모두)

| 차원 | 사용자에게 보이는 이름 | 묻는 질문 | 시주 의존 |
| --- | --- | --- | --- |
| communication | 대화의 결 | 말하는 방식과 듣는 방식이 맞물리는가 | 낮음 |
| emotional | 감정의 온도 | 감정을 느끼고 드러내는 속도가 비슷한가 | 중간 |
| pace | 생활의 속도 | 결정하고 움직이는 속도가 맞는가 | 낮음 |
| friction | 부딪히는 지점 | 어떤 상황에서 마찰이 생기는가 | 중간 |

### 가족에서 추가되는 차원

| 차원 | 사용자에게 보이는 이름 | 묻는 질문 | 시주 의존 |
| --- | --- | --- | --- |
| expectation | 기대와 역할 | 서로에게 무엇을 기대하고 어떤 역할을 떠맡는가 | 중간 |
| support | 버팀목의 방식 | 힘들 때 어떻게 도우려 하고, 어떤 도움을 받고 싶어하는가 | 높음 |
| boundary | 거리의 감각 | 간섭과 관심의 경계를 어디에 두는가 | 중간 |

### 친구에서 추가되는 차원

| 차원 | 사용자에게 보이는 이름 | 묻는 질문 | 시주 의존 |
| --- | --- | --- | --- |
| play | 함께 노는 방식 | 어떤 활동에서 서로 즐거운가 | 낮음 |
| loyalty | 곁에 있는 방식 | 자주 연락하는 친구인가, 오래 두어도 괜찮은 친구인가 | 중간 |
| honesty | 솔직함의 수위 | 쓴소리를 주고받을 수 있는 사이인가 | 중간 |

### 연인에서 추가되는 차원

| 차원 | 사용자에게 보이는 이름 | 묻는 질문 | 시주 의존 |
| --- | --- | --- | --- |
| affection | 애정 표현 | 사랑을 표현하고 확인받고 싶어하는 방식이 맞는가 | 높음 |
| closeness | 가까움과 거리 | 붙어 있고 싶은 정도와 혼자 있고 싶은 정도가 맞는가 | 높음 |
| future | 앞을 보는 눈 | 관계의 다음 단계를 생각하는 속도가 비슷한가 | 중간 |
| conflict | 다툰 뒤의 회복 | 다투고 나서 어떻게 풀어가는가 | 중간 |

### 직장동료에서 추가되는 차원

| 차원 | 사용자에게 보이는 이름 | 묻는 질문 | 시주 의존 |
| --- | --- | --- | --- |
| role | 역할의 맞물림 | 일을 나눌 때 누가 앞장서고 누가 받쳐주는 쪽이 자연스러운가 | 낮음 |
| decision | 결정의 방식 | 빨리 정하고 고쳐가는 편인가, 충분히 보고 정하는 편인가 | 낮음 |
| feedback | 피드백의 온도 | 지적을 주고받을 때 어떤 방식이 덜 상하는가 | 중간 |
| distance | 일과 사적인 거리 | 일 밖에서도 가까워지길 바라는가, 일로만 만나길 바라는가 | 중간 |
| pressure | 압박 속의 모습 | 마감이나 갈등 상황에서 각자 어떻게 달라지는가 | 높음 |

직장동료 유형에서는 8절의 금지 표현이 특히 중요하다. "누가 더 유능한가", "누가 리더에 맞는가"로 읽힐 수 있는 문장은 쓰지 않는다. 해설은 두 사람이 함께 일할 때의 방식에 머문다.

시주 의존이 "높음"인 차원은 한쪽이라도 출생시간이 없으면 결과에서 "추정"으로 표기하거나 숨긴다(5절).

### 해설 문장의 구조

각 차원의 해설은 세 문장을 넘지 않고, 아래 순서를 지킨다.

1. **관찰** — 두 사람 각자가 이 차원에서 어떤 사람인지 한 문장씩. "A는 결론부터 말하는 편이고, B는 맥락을 먼저 깔고 말하는 편입니다."
2. **맞물림** — 그 둘이 만나면 어떤 장면이 생기는지. "그래서 B는 A가 성급하다고 느끼고, A는 B가 답답하다고 느낄 수 있습니다."
3. **다루는 법** — 그 장면에서 무엇을 하면 좋은지. "중요한 이야기는 A가 결론을 잠시 미루고 B의 맥락을 끝까지 듣는 것만으로 달라집니다."

세 번째 문장이 이 서비스의 상품이다. 점수는 세 번째 문장을 읽게 만드는 입구일 뿐이다.

### 점수의 표현

차원별 점수는 내부적으로 0~1 실수로 계산하되, 사용자에게는 숫자 대신 세 단계로 보여준다. "잘 맞아요 / 다른 결이에요 / 부딪힐 수 있어요". 숫자는 비교와 서열을 낳고, 가족·친구·연인 관계에서 서열은 상처가 된다. 관계 전체를 하나의 숫자로 합산한 "총점"은 만들지 않는다.

## 8. 결과 카드와 톤 가이드

결과 카드는 두 겹이다. 겉장은 10초 안에 읽히고 공유하고 싶게, 속장은 다시 돌아와 읽고 싶게 만든다.

### 카드의 두 겹

| | 겉장 (공유되는 부분) | 속장 (서비스 안에서만) |
| --- | --- | --- |
| 담는 것 | 두 사람의 호칭, 관계 유형, 헤드라인 한 줄, 가장 잘 맞는 차원 하나, 가장 부딪히는 차원 하나 | 모든 차원의 관찰·맞물림·다루는 법, 다른 유형으로 보기, 신뢰도 안내 |
| 길이 | 40자 이내 헤드라인 + 차원 이름 두 개 | 차원당 세 문장 |
| 목적 | "이거 봐" 하고 보내게 만드는 것 | "그래서 어떻게 하라는 거지"에 답하는 것 |
| 원천정보 | 없음 | 없음 |

헤드라인 예시: "결론부터 말하는 사람과 맥락부터 까는 사람", "서로 다른 속도로 같은 곳을 보는 사이". 두 사람을 한 쌍의 대비로 묘사하되, 어느 쪽도 좋고 나쁜 쪽이 되지 않게 쓴다.

### 문장 원칙

- 한 문장은 25자 안팎. 두 번 읽어야 이해되는 문장은 다시 쓴다.
- 전문 용어 금지. "일간", "월령", "편관", "오행 상극" 같은 단어는 속장에도 쓰지 않는다. 사용자가 그 단어를 찾아봐야 한다면 실패다.
- 상대를 설명할 때는 행동으로 쓴다. "내향적입니다"가 아니라 "혼자 정리할 시간이 있어야 다음 말이 나옵니다".
- 단정하지 않는다. "~입니다" 대신 "~한 편입니다", "~할 수 있습니다". 성향은 경향이지 판결이 아니다.
- 세 번째 문장(다루는 법)은 반드시 양쪽 모두가 할 수 있는 행동 하나로 끝난다. 한쪽에게만 바뀌라고 하지 않는다.

### 금지 표현

| 금지 | 이유 | 대신 |
| --- | --- | --- |
| 총점, 등급, "OO점", "S급" | 관계에 서열을 매긴다 | 차원별 세 단계 표현 |
| "운명", "천생연분", "악연", "상극" | 예언과 판결의 언어 | "결이 맞는", "다른 결의", "부딪힐 수 있는" |
| "헤어지는 게", "멀리하세요" | 관계를 끊으라는 조언은 하지 않는다 | 마찰을 다루는 행동 제안 |
| "~해야 합니다" | 명령조 | "~하면 달라집니다", "~해보는 것도 방법입니다" |
| 건강·금전·수명에 관한 언급 | 서비스 범위 밖, 법적 위험 | 다루지 않는다 |
| 상대의 생년월일·출생시간·띠 | 원천정보 노출 | 다루지 않는다 |

### 결과 하단의 고정 문구

모든 속장 하단에 같은 문구를 둔다. "이 해석은 두 분의 타고난 성향을 바탕으로 한 참고 자료이며, 관계를 판단하거나 미래를 예측하지 않습니다." 서비스 소개 문서의 원칙을 사용자 화면에서 반복하는 것이다.

## 9. MVP에서 뺀 것

아래는 특허 문서나 서비스 소개에 있지만 첫 버전에서 의도적으로 뺀 것이다. 빠진 이유가 사라지면 그때 넣는다.

| 뺀 것 | 이유 | 들어오는 조건 |

| 네이티브 앱(iOS/Android) | 스토어 심사, 연락처 권한, 결제 연동이 한꺼번에 붙는다. 웹 링크만으로 핵심 흐름이 검증된다 | 웹에서 재방문율과 관계 등록 수가 확인된 뒤 |
| 연락처 자동 연동 | 가장 민감한 권한. 첫 버전은 사용자가 상대 이름을 직접 입력한다 | 앱 전환 시, 해시 기반 매칭 설계와 함께 |

| 본격 비즈니스 관계 유형(동업·거래처·투자자) | 가까운 사이와 직장동료에서 레퍼런스가 쌓인 뒤 니즈가 생길 때 | 직장동료 유형의 사용 패턴이 보일 때 |
| 관계 이벤트·타임라인 | 관계가 쌓여야 의미가 있다. 테이블만 설계해 둔다 | 활성 관계의 평균 수명이 한 달을 넘을 때 |
| 관측 기반 신뢰도 | 이벤트가 없으면 관측도 없다 | 관계 이벤트와 함께 |
| 관계 그래프 시각화(노드·엣지 그림) | 등록 인원 5명 이하에서는 목록이 더 낫다 | 사용자당 평균 등록이 5명을 넘을 때 |
| AI 생성 해설 | 첫 버전은 차원별 규칙과 문장 템플릿으로 만든다. 품질과 비용을 통제하기 위해서 | 템플릿 해설의 한계가 사용자 피드백으로 확인될 때 |
| MBTI 등 두 번째 해석 엔진 | 엔진 인터페이스만 고정하고 구현은 하나 | 첫 엔진의 해설 품질이 안정된 뒤 |
| 출생지역·진태양시 보정 | 정밀도보다 흐름 검증이 먼저 | 해석 엔진 고도화 단계 |

AI 생성 해설을 뺀 결정은 다시 논의할 여지가 있다. 템플릿은 통제가 쉽지만 문장이 반복되고, 생성형은 풍부하지만 톤과 금지 표현을 지키게 하는 비용이 든다. 첫 버전은 템플릿으로 시작하되, 두 번째 사용자 테스트 전에 생성형 해설을 일부 차원에 시험한다.
